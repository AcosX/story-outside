# 结局与性能修复

基线：main `4135178`。本次修复针对自然收束、结局对照、知乎讨论/知识及长会话写入。

## 行为

- 主要目标完成后提示导演直接收束，不再开启下一副本。第10次选择后向高潮推进，第16次后收束，第24次及明确结束请求必须输出结束工具。此节奏与 advisory `story_progress` 独立。
- 只有终结批次的最后一条叙事提交后才进入 `finished`；此前仍可打断。旧记录的已提交 `finish_envelope` 在加载时恢复终态，阻止继续生成。
- 结局对照接受原作正文和官方导语，展示引文来源。缺少正文后续时仍利用导语中明确的结局；首次偏离必须对应真实已提交玩家事件。没有可核实节点时解释具体资料边界，不制造偏离。
- 旧结局通过受会话所有权保护的 `/api/sessions/:uuid/ending-analysis` 后台补分析。作品原结局与会话分析分别缓存，包含来源、历史、模型和规则版本；不改写玩家历史。页面先渲染原有结局，随后补充分析和生态结果。
- 讨论使用官方 `developer.zhihu.com/api/v1/content/zhihu_search`，Bearer Access Secret 和秒级时间戳。复用已有受保护配置；不需要变更 OAuth 凭证。
- 知识接通赛事 `knowledge/list` 与详情；目录共享缓存并合并并发请求，按查询匹配。目录未覆盖的主题使用真实知乎搜索结果延伸。知识正文保留作者/来源。失败不冒充真实数据。

## 性能证据与边界

线上日志显示 SQL 约 0.1 秒，Galera 提交约 7.6 秒；一次模型生成约34秒。458事件的会话运行时为1,419,471字节，主要是幂等重放缓存；并非MariaDB未启用。

将请求重放/摘要审计缓存编码为带版本的 gzip JSON，保留所有结果与指纹；正文仍保存在 append-only `session_events`，状态和结局保持可查询。兼容读取旧 JSON，拒绝损坏或未知编码。

VM3 独立测试库用同一会话负载交替测试两次：

| 存储 | 字节 | 提交耗时 |
|---|---:|---:|
| 原 JSON | 1,419,471 | 5,334 / 4,965 ms |
| gzip JSON | 308,376 | 1,098 / 1,150 ms |

该负载写入体积及提交耗时约下降78%，读回逐字段一致。这是隔离库微基准，不等同于线上端到端响应时间。模型生成时间不因此减少。

模型上下文保留完整原作和已提交历史，去掉重复的生成开场资产，明确列出玩家选择序号；结局分析不阻塞主页面。SQL已经使用异步I/O，玩家事件仍须等事务提交成功才确认；后台不可靠写入无法保持断线重试和重启恢复承诺。后续规模增长仍需把大规模重放缓存拆为增量记录，并减少全量内存快照扫描；现阶段不宣称架构最优。

## 回滚

没有DDL迁移。旧发行版不认识 `replay_cache` 编码。回滚到旧代码前，应停止部署定时器和业务写入进程，以同一数据库环境运行当前版本的 `node scripts/expand-runtime-replay.mjs`（只读检查），再运行 `node scripts/expand-runtime-replay.mjs --apply` 解压回旧JSON。出现错误必须停止回滚；不得跳过失败继续启动旧版本。确认无编码行后才切回旧发行版并恢复原定时器/业务服务。脚本保留所有玩家事件，不删除数据。

验证：全套本地测试、155文件语法检查及VM3全新独立数据库集成测试通过。真实模型在核心目标已完成、玩家只输入“继续”的短场景中主动结束（16.7秒）；这不是所有故事的自然结束成功率保证。部署脚本scripts/vm3-deploy.sh在运行时回滚前停止写入并展开缓存，隔离库逐字段验证还原通过。
